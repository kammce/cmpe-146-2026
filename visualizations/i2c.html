How it works

One bus, no chip select. Unlike SPI, both devices share just two wires (SCL and SDA, both pulled up to idle HIGH) and there is no per-device select line at all. Every transaction starts with a START condition (SDA falls while SCL is high), then the controller clocks out a byte containing a 7-bit address plus a read/write bit. Only the device whose address matches drives SDA low on the very next clock (an ACK) — everyone else leaves it alone, and the pull-up keeps it high (a NACK). That single ACK/NACK bit is what "chip select" gets replaced with.

Light Sensor (0x23). A tiny register map: 0x00 WHO_AM_I (read-only, always 0x53), 0x01 CONFIG (read/write, bit0 = power), 0x02/0x03 LUX_H/LUX_L (read-only, unsigned 16-bit, 1 lux/LSB, MSB first). Writing follows the common convention real I2C sensors use: the first byte you Write sets an internal register pointer, and any further bytes in that same Write land in consecutive registers from there. The pointer is real, persistent state — it stays put after the bus goes idle, so a plain Read later picks up wherever it was left, exactly like the datasheet for a real sensor would describe. The sensor reads back all zeros while CONFIG's power bit is off, so Write CONFIG=0x01 before expecting a real LUX value.

Read Register (repeated START). The most common real-world I2C pattern is one unbroken transaction: START, address + write, the register pointer byte, a repeated START (no STOP in between — the bus is never released), address + read, then the data bytes. That's exactly what this button scripts as a single queued waveform, letting you watch the "Sr" marker and the direction flip from W to R without the bus ever going idle.

Accelerometer (0x68). Its own, completely independent register space on the same two wires — same shape as the light sensor's (0x00 WHO_AM_I, 0x01 CONFIG with a power bit, data registers from 0x02), because that's a genuinely common convention, not a coincidence of this simulator. It needs to be powered on the same way: Write CONFIG=0x01 before X/Y/Z means anything, otherwise every axis reads zero. The three axes are 0x02–0x07 (X, then Y, then Z, each signed 16-bit, 1 mg/LSB, MSB first) — reading 6 bytes starting at 0x02 bursts all three out in one transaction, the classic way real accelerometer drivers grab a full sample. At rest Z reads close to +1000 mg (gravity) while X and Y hover near zero, all three drifting slightly to simulate a hand that isn't perfectly still.

Addressing anything nobody owns — like the "No Device" preset at 0x10 — still always ends in a NACK right after the address byte — a very real scenario on an actual bus when a part is missing, unpowered, or you simply typed the wrong address.

Each data byte the controller reads gets ACKed by the controller itself to ask for more, except the very last one, which it deliberately NACKs to tell the slave to stop and release the bus for the STOP condition — watch for that on the final byte of every Read.
