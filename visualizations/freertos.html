How it works

One CPU, one running task. This is a single-core simulation: at any given tick, exactly one of these three tasks actually owns the CPU (highlighted with a yellow current-line marker, like a debugger's program counter), and it is always the highest-priority task that is currently ready to run. Task A and Task B share priority 1; the built-in idle task always exists at priority 0, the lowest possible, so it only ever runs when nothing else can.

vTaskDelay() blocks, it doesn't busy-wait. When a task calls vTaskDelay(N), it voluntarily gives up the CPU for the next N ticks — it moves to the BLOCKED state, and the scheduler is free to run something else. The task's code stays paused exactly at that call (the dim yellow marker in its code panel) until N ticks have actually elapsed, at which point it becomes ready again.

Where idle comes in. If both Task A and Task B are blocked at the same time — which will happen constantly once they're running on different periods — there is nothing else at priority 1 to run, so the scheduler falls back to the idle task. It just spins, tick after tick, doing nothing, until one of the delays expires. The instant that happens, the newly-ready task preempts idle immediately (idle never gets to choose whether to give up the CPU — anything higher priority always wins) and resumes exactly where it left off, right after its vTaskDelay() call.

What each task is actually doing. Both Task A and Task B toggle their own GPIO pin every time they wake up -- watch the small LED next to each task's name flip on and off in step with its highlighted toggle line. The default delays (20 and 14 ticks) are deliberately small so a handful of full wake/toggle/ sleep cycles happen quickly; type in something like 500 to see the same thing play out on more realistic real-world numbers. Notice that Run doesn't move at one fixed pace: CPU Instruction Speed controls how long each line of Task A or B's own code stays on screen while one of them has the CPU, and Idle Fast-Forward Speed separately controls how quickly ticks pass while idle is just spinning with nothing to do. Turn the first one up to slowly watch every line get entered; turn the second one down so you're not stuck watching hundreds of uneventful idle ticks between the interesting parts.

Try it: set Task A and Task B to the same delay and watch them wake on the same tick every cycle (ties are broken by task order here, a simplification of real round-robin behavior between equal-priority tasks). Set them to very different values and watch the trace below fill mostly with idle time punctuated by short bursts of A or B. Use Step to advance exactly one tick at a time, like a debugger, or Run to let it play continuously.
