How it works

Shared bus, two chip selects. Both devices sit on the same SCK, COPI, and CIPO wires, but each has its own independently-toggleable CS button. Normally you'd only ever assert one at a time — an unselected device sees the same SCK/COPI clocking as everyone else but ignores it and never drives CIPO. If you assert both CS lines at once (a real wiring or firmware bug), the graph and schematic flag it: CIPO turns into a pulsing red "BUS CONTENTION" indicator, because you no longer know which chip (if either) is actually driving that wire.

One command per chip-select session. Each device only pays attention to the very first Write it sees after its CS goes low — every Write after that is silently ignored, no matter what's in it, until you release and re-assert CS. If that first command isn't one the device recognizes, you get nothing: e.g. select the GPIO expander and Write [0x25] then [0xFF] — the moment 0x25 lands, the device is done for this session, and the 0xFF right behind it (and any Read after) is ignored too. If the first command is valid, it earns exactly one Read to collect the result (if the command needs one) — once that Read happens, the device locks out the same way. This is on purpose: real SPI peripherals expect one clean transaction per CS assertion, and always de-asserting CS when you're done is the habit this is here to build.

Temp Sensor. Assert its CS, then Write [0xC1, 0xA5] (command 0xC1 = read-back, address 0xA5) to arm a temperature reading, or Write [0x51] to arm a humidity reading instead (unsigned 16-bit, 0.01%RH per LSB). While CS stays asserted, pressing Read clocks out whichever 2-byte value was armed on CIPO. Both readings drift slowly on their own unless you check their Override boxes.

Why 0x51 twice? The humidity command deliberately reuses the GPIO expander's own 0x51 "arm a Read" opcode. On its own that's harmless — each chip only listens on its own CS. But if you assert both CS lines and Write [0x51], you'll arm both devices at once, and the next Read triggers the bus contention above. That's the whole reason chip selects exist: two devices can happily share the same three wires as long as exactly one of them is ever listening.

GPIO Expander. An 8-bit output register that persists forever (it does not reset when its CS is released, unlike the sensor's arm state). Write [0x50, value] to set all 8 outputs at once, or Write [0x51] to arm it, then Read 1 byte to shift the current register value back out on CIPO — either way, that's this session's one command. The LEDs (on its chip and in the devices panel) only update once the relevant byte has actually finished clocking across the wire, not the instant you click Write — watch the trace to see exactly when the change lands. To flip just one bit without disturbing the others, use "Toggle Bit": it runs the real read-modify-write a driver would — Read the current output, flip one bit in software, then Write the whole byte back — as two separate CS-bracketed transactions (since one CS session only ever gets one command now), releasing and re-asserting the GPIO's CS in between. Watch the CS-G lane drop between the two halves on the trace. It only runs when both CS lines start out released, so it can't collide with anything in progress or trigger contention.

SPI Mode controls when data is sampled/shifted relative to the clock edge (CPOL/CPHA) — try switching modes and watch the COPI/CIPO edges move relative to SCK. Use Graph Zoom to widen individual clock edges.
